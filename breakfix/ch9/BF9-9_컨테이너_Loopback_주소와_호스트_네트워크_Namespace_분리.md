# BF9-9. 컨테이너 Loopback 주소와 호스트 네트워크 Namespace 분리

## 1. 개요

| 항목 | 내용 |
|---|---|
| 환경 | Rocky Linux 8.10 / Podman 브리지 네트워크 |
| 증상 | 호스트에서는 접속되는 백엔드가 컨테이너에서는 `Connection refused` 반환 |
| 원인 | 컨테이너의 `127.0.0.1`이 호스트의 Loopback을 가리키지 않음 |
| 해결 | 호스트 네트워크 사용 또는 브리지 주소에 백엔드 바인딩 |

## 2. 문제 현상

동일한 `127.0.0.1:18941`을 대상으로 했지만 실행 위치에 따라 결과가 달랐다.

```text
호스트에서 요청       : HTTP 200
브리지 컨테이너에서 요청: Connection refused
```

## 3. 원인 분석

확인한 네트워크 주소는 다음과 같다.

```text
호스트 브리지(cni-podman0): 10.88.0.1/16
컨테이너 IP            : 10.88.0.2
```

- 브리지 컨테이너는 독립적인 Network Namespace를 사용한다.
- 컨테이너 안의 `127.0.0.1`은 **호스트가 아닌 컨테이너 자신**이다.
- 호스트 백엔드가 `127.0.0.1`에서만 수신한다면 컨테이너에서 `10.88.0.1`로 요청해도 해당 주소에 리스너가 없어 연결되지 않는다.

## 4. 해결 과정

실습에서는 두 가지 연결 경로를 각각 확인했다.

1. `--network host`를 사용해 호스트의 Loopback 서비스에 접속했다.
2. 브리지 네트워크에서는 백엔드가 `10.88.0.1:18941`에서 수신하도록 구성한 뒤 컨테이너 `10.88.0.2`에서 연결했다.

이는 같은 주소에 무조건 재요청하는 대신 **요청 주체의 Network Namespace와 서버의 수신 주소**를 함께 수정한 조치다.

## 5. 결과

- 호스트 네트워크 컨테이너의 Loopback 접근 성공(`CONNECT_OK`) 확인.
- 브리지 컨테이너 `10.88.0.2`에서 `10.88.0.1:18941` 요청 시 HTTP `200 OK` 확인.
