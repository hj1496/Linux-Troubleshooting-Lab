# BF 1-5. 서비스 포트 충돌과 메모리 사용량 증가

## 1. 개요

| 항목 | 내용 |
|---|---|
| 환경 | Rocky Linux 8.10 (`node1`) |
| 증상 | API 서비스 실행 실패, 별도 Python 프로세스의 메모리 점유 |
| 목표 | 두 증상의 원인과 연관성을 구분하고 서비스 복구 |
| 진단 | 서비스 오류, 포트 점유, 프로세스 계보 및 메모리 사용량 조사 |

## 2. 문제 현상

`rh342-api.service`에서 HTTP 서버를 실행하지 못했다.

```text
OSError: [Errno 98] Address already in use
```

서비스의 실행 명령은 다음과 같았다.

```bash
python3 -m http.server 18080 --bind 127.0.0.1
```

동시에 별도 Python 프로세스(PID 1703)가 약 120 MiB의 메모리를 사용하고 있었다.

## 3. 원인 분석

### ① API 서비스 실패 원인 확인

```bash
ss -tuln
```

- `127.0.0.1:18080` 포트가 이미 LISTEN 상태였다.
- `/run/rh342-port-holder.py`가 해당 주소와 포트를 선점하고 있었다.
- API 서비스는 동일한 주소와 포트에 바인딩하려다 `Errno 98` 오류로 실패했다.

### ② 메모리 점유 프로세스 조사

```bash
pstree -sp 1703
```

프로세스 관계:

```text
systemd → timeout(1684) → python3(1703)
```

Python 실행 내용에는 다음과 같은 메모리 할당이 포함되어 있었다.

```python
bytearray(120*1024*1024)
```

PID 1703의 메모리 점유는 API 서비스의 포트 충돌과 별개의 현상이었다.

### ③ 두 증상의 연관성 판단

| 항목 | 관찰 시점 | 확인된 원인 |
|---|---|---|
| API 서비스 실패 | 16:52 | 포트 18080 선점 |
| Python 메모리 점유 | 18:32 시작 | 별도 메모리 할당 작업 |

메모리 점유 프로세스는 서비스 실패 이후에 시작되었다. 따라서 메모리 점유를 API 서비스 실패의 직접 원인으로 볼 수 없었다.

## 4. 해결 과정

1. `127.0.0.1:18080`을 선점하던 port-holder 프로세스를 종료했다.
2. `rh342-api.service`를 재시작했다.
3. 메모리 점유 작업은 `timeout`에 의해 종료되었다.

복구 상태를 다음 명령어로 확인했다.

```bash
systemctl status 'rh342*'
ss -tulnp
free -h
```

## 5. 결과

- `rh342-api.service`가 `active (running)`으로 복구되었고, Main PID는 `1798`이었다.
- `127.0.0.1:18080`에서 API 서비스의 Python 프로세스(PID `1798`)가 LISTEN 중임을 확인했다.
- 별도 메모리 점유 작업 종료 후 `free -h`의 used 메모리가 `207 MiB`로 감소했다.
